# 版本、分支与备份约定

## 三种标识各有用途

| 标识 | 作用 | 例子 |
| --- | --- | --- |
| 更新编号 | 标识一项逻辑工作，关联记录、分支、提交和 PR | `JN-0001` |
| Git 提交号 | 唯一标识一份实际提交及其父历史 | 通过 `git rev-parse HEAD` 获取 |
| 发布版本/标签 | 标识经过验收、需要交付的里程碑 | 将来使用 `v0.1.0`；当前没有应用发布版本 |

不要每改一行就新增一个任务编号；同一项工作有多次提交，继续写原记录。新的独立需求或已经关闭工作的新缺陷才分配新编号，并引用前一个编号。重复运行同一测试不等于新的产品版本。

## 开工与防重复

1. 检查工作区和 `origin`，保留已有改动；执行 `git fetch origin --prune`。
2. 查看 `git branch -a`、`git log --all --oneline --decorate -20`、更新目录和已有 PR，先确认需求是否已完成或正在处理。
3. 同一任务继续原编号/分支。新任务使用已知最大编号加一，至少四位数字，并立即创建对应记录及主题分支。记录现有分支和提交作为起点。
4. 多电脑或多人并行时先核对活动分支中的编号。编号规则不是分布式锁；若同号冲突，尚未集成的一方更换编号并写明关联，禁止覆盖已有记录。新分支第一笔记录提交后及时同步，使其他参与者可见。
5. 搬到另一台电脑继续时，检出原分支；不要重新初始化同一项目、复制另一套源码或重新实现已存在的内容。

## 分支约定

- `main`：已集成的稳定进度。当前初始空仓库直接建立一次基线；后续日常修改走主题分支。
- `feat/JN-0002-short-name`：新功能；`fix/JN-0003-short-name`：修复；`docs/...`：文档；`chore/...`：工具或依赖维护。示例编号不代表已分配。
- 默认从更新后的 `main` 建分支；若依赖未合并任务，明确记录依赖分支和起点提交，不假装互相独立。
- 每个主题分支通过 PR 或经核对的合并进入主干，优先保留原提交的合并方式。合并状态和部署状态分别报告。
- 不长期复制多条“最新版主线”；不擅自删除仍有独有提交的分支，不强推共享历史。分支保护必须在 GitHub 实际设置后才能声称已启用；本次未配置分支保护。

## 每项更新必须记录

复制 [更新模板](templates/change.md) 到 `docs/changes/JN-NNNN.md`，填写：

- 目标、范围、编号、日期、分支、起点和依赖。
- 具体改动，以及哪些只是方案、哪些已实际实现。
- 实际执行的验证、结果与局限；未执行的检查明确写明。
- 数据结构/数据迁移是否变化、如何回退、会影响哪些配置或文件。
- 未完成事项、下一步和必要的替代/关联编号。

记录中的“完成”描述工作内容，不代表自动发布。提交号、PR、远端分支与 CI 是动态状态，应从 Git/GitHub 现场核对。不要为把当前提交号写进当前提交而不断新增“记录提交号”的提交。

```bash
# 查看一个编号对应的实际提交（包括修补）
git log --all --oneline --fixed-strings --grep="(JN-0001):"
# 查看更新记录自身的历史
git log --follow -- docs/changes/JN-0001.md
```

## 提交、推送与交付

普通提交格式：`type(JN-NNNN): 具体变化`。常用 type 为 feat、fix、docs、chore、refactor、test；合并与 revert 提交保留来源信息。

1. 审查实际 diff 与文件范围，确认没有业务原件、凭据和无关改动。
2. 更新该编号的记录；若方向或整体进度改变，同时更新 `docs/project-context.md`。
3. 运行 `python scripts/check_history.py`，并执行与当前改动相符的功能测试。失败或未验证不能写成通过。
4. 明确暂存文件，审查 `git diff --cached`，再提交。推送前再次获取远端；发生分叉先读差异，不直接覆盖。
5. 推送后用 `git rev-parse HEAD` 和 `git ls-remote origin refs/heads/<branch>` 比对提交号，并检查 CI。遇到网络失败或检查失败，明确记录状态。
6. 向用户交付：更新编号、实际分支、提交号/链接、变化、验证、远端同步状态和剩余事项。应用上线需要另外报告实际部署证据。

CI 检查记录结构、编号和变更记录是否随提交批次出现，并提示已跟踪文件是否命中忽略规则。这些检查能拦截常见遗漏，不能证明所有描述真实、所有资料安全或业务无重复。

## 回退与发布

- 用新的 `git revert` 提交撤回错误，保留原始历史；涉及合并提交时先确认应保留的父分支。
- 应用发布时，记录发布标签、源码提交、实际构建产物与必要的数据迁移。标签创建后不移动、不重复使用。
- 数据迁移和文件删除不能靠代码 revert 自动恢复；必须先确认对应备份及恢复步骤。当前未建设数据库，不虚构数据恢复能力。

## 防丢与换电脑

| 内容 | 保存与核对方式 |
| --- | --- |
| 源码、通用配置、开发记录 | Git 提交并推送；验证远端提交号；必要时另存并验证 `git bundle` |
| 尚未提交/未推送的改动 | 离开旧电脑前列出并保存；能提交的提交，剩余内容单独复制并核对 |
| 内部规划、业务原件、上传文件 | 独立快照与 SHA-256 清单，保留原路径关系；不要推到公开仓库 |
| 数据库与附件关系 | 应用建成后实施一致的数据库/文件备份，并在隔离环境实际恢复验证 |
| 密钥与运行环境 | 密钥通过受控配置恢复；仓库只存不含凭据的模板和依赖清单 |
| 完整聊天和附件 | 独立确认应用支持和实际可访问性；项目摘要只恢复必要上下文 |

本地第二份快照只能防部分误操作，不能覆盖电脑损坏或丢失。内部资料仍需要由用户确认的异地/另一设备备份位置；在此之前不要声称完整容灾已完成。

换电脑时先克隆仓库、检出未完成工作的原分支，再复制内部资料/必要数据与配置；核对提交号和文件校验值，有应用后再实际启动验证。旧电脑原件保留到核对完成。
